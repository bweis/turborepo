Boundaries ensure that Turborepo features work correctly by checking for package manager Workspace violations.

```bash title="Terminal"
turbo boundaries
```

<Callout type="info" title="Boundaries RFC">
  This feature is experimental, and we're looking for your feedback on [the
  Boundaries RFC](https://github.com/vercel/turborepo/discussions/9435).
</Callout>

This command will notify for two types of violations:

- Importing a file outside of the package's directory
- Importing a package that is not specified as a dependency in the package's `package.json`

## TypeScript path aliases

Imports that match a `paths` entry in the package's `tsconfig.json` are resolved before they're checked:

- An alias that resolves to a file inside the package is a local import.
- An alias that resolves into another workspace package is treated as an import of that package, so it's allowed when that package is a dependency and reported as an undeclared dependency otherwise.
- An alias that resolves to a file outside of every workspace package is reported as importing a file outside of the package's directory.

For example, with `"@ui/*": ["../../packages/ui/src/*"]` in `apps/web/tsconfig.json`, `import { Button } from "@ui/button"` is an import of the package in `packages/ui` (for example, `@repo/ui`), so `apps/web` needs `@repo/ui` in its `package.json` dependencies.

Specifiers that walk up the directory tree with `..` (like `@/../../packages/ui/src/button`) are always reported as leaving the package, even when they start with an alias.
## Ignoring files

To skip an individual import, add a `// @boundaries-ignore <reason>` comment on the line above it.

Some files, like generated code (for example, TanStack Router's `routeTree.gen.ts`), can't keep comments because they're rewritten on every build. Use `boundaries.ignore` to skip them entirely:

```json title="./turbo.json"
{
  "boundaries": {
    "ignore": ["**/routeTree.gen.ts"]
  }
}
```

Globs are matched relative to each package's directory. Globs in the root `turbo.json` apply to every package, and globs in a package's `turbo.json` apply to that package in addition to the root globs:

```json title="./apps/web/turbo.json"
{
  "extends": ["//"],
  "boundaries": {
    "ignore": ["src/generated/**"]
  }
}
```

Ignored files aren't parsed, so none of their imports are checked, and they don't count towards the number of checked files. Negated globs (`!`) and globs that point outside the package (starting with `..`) aren't supported.

If you use a [baseline](#adopting-boundaries-in-an-existing-repository), ignoring a file that has baselined violations makes those entries stale, so run `turbo boundaries --update-baseline` after adding the glob.

## Tags

Boundaries also has a feature that lets you add tags to packages. These tags can be used to create rules
for Boundaries to check. For example, you can add an `internal` tag to your UI package:

```json title="./packages/ui/turbo.json"
{
  "tags": ["internal"]
}
```

And then declare a rule that packages with a `public` tag cannot depend on packages with an `internal` tag:

```json title="./turbo.json"
{
  "boundaries": {
    "tags": {
      "public": {
        "dependencies": {
          "deny": ["internal"]
        }
      }
    }
  }
}
```

Alternatively, you may want `public` packages to only depend on other `public` packages:

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "public": {
        "dependencies": {
          "allow": ["public"]
        }
      }
    }
  }
}
```

Likewise, you can add restrictions for a tag's dependents, i.e. packages that import packages with the tag.

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "private": {
        "dependents": {
          "deny": ["public"]
        }
      }
    }
  }
}
```

Package names can also be used in place of a tag in allow and deny lists.

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "private": {
        "dependents": {
          "deny": ["@repo/my-pkg"]
        }
      }
    }
  }
}
```

Tags allow you to ensure that the wrong package isn't getting imported somewhere in your graph. These rules are
applied even for dependencies of dependencies, so if you import a package that in turn imports another package
with a denied tag, you will still get a rule violation.

### Assigning tags by directory

If your tags follow from where packages live in your repository, you can assign them from the root `turbo.json`
with `packageTags` instead of adding a `turbo.json` to every package:

```json title="./turbo.json"
{
  "boundaries": {
    "packageTags": {
      "apps/*": ["app"],
      "packages/server/*": ["node"],
      "packages/**": ["library"]
    },
    "tags": {
      "library": {
        "dependencies": {
          "allow": ["library"]
        }
      }
    }
  }
}
```

Each key is a glob matched against package directories relative to the repository root. A package receives the
tags of every glob that matches its directory, combined with any `tags` in its own `turbo.json`. In this example,
a package in `packages/server/api` has both the `node` and `library` tags.

`packageTags` can only be used in the root `turbo.json`. `turbo boundaries` reports invalid globs as errors, and
warns about globs that don't match any package so that your configuration doesn't silently drift from your
repository's layout.

### Denying npm packages

Use `denyPackages` in a `dependencies` rule to ban external (npm) packages. Entries can be package names or globs.
For example, to make sure packages tagged `browser` never depend on server-only packages:

```json title="./turbo.json"
{
  "boundaries": {
    "tags": {
      "browser": {
        "dependencies": {
          "denyPackages": ["pg", "drizzle-*", "@aws-sdk/*"]
        }
      }
    }
  }
}
```

`denyPackages` is checked against the external dependencies declared in the `package.json` of the package and of
every Workspace package it depends on, directly or transitively. If `@repo/web` is tagged `browser` and depends on
`@repo/ui`, which depends on `@repo/db`, which declares `pg`, `turbo boundaries` reports that `@repo/web` depends on
`pg` through `@repo/db`.

A few things to keep in mind:

- For the package the rule applies to, all dependency fields are checked: `dependencies`, `devDependencies`,
  `optionalDependencies`, and `peerDependencies`.
- For the Workspace packages it depends on, `devDependencies` are skipped, since they're never installed for or bundled
  into their dependents. Their `dependencies`, `optionalDependencies`, and `peerDependencies` are checked.
- The Workspace packages that are checked are found the same way as for tag rules, including packages that are only
  reached through a `devDependencies` entry. For example, if `@repo/web` lists `@repo/test-utils` in its
  `devDependencies`, the npm packages `@repo/test-utils` declares in `dependencies` are still checked.
- npm aliases are matched by both the declared name and the aliased package, so `"db": "npm:pg@^8"` is denied by
  `"pg"`.
- In globs, `*` doesn't match `/`, so `@aws-sdk/*` matches `@aws-sdk/client-s3`, and `drizzle-*` matches
  `drizzle-orm` but not `@scope/drizzle-orm`.
- `denyPackages` only applies to external packages. To deny Workspace packages, use their names in `deny`.
- `denyPackages` can only be used in `dependencies` rules, not in `dependents` rules.

You can also use `denyPackages` in a package's own `turbo.json`:

```json title="./apps/web/turbo.json"
{
  "boundaries": {
    "dependencies": {
      "denyPackages": ["pg"]
    }
  }
}
```

## Disabling import checks

If you'd like to adopt tag rules before fixing every import violation, you can turn off the import checks by setting `importChecks` to `false` in your root `turbo.json`:

```json title="./turbo.json"
{
  "boundaries": {
    "importChecks": false,
    "tags": {
      "public": {
        "dependencies": {
          "deny": ["internal"]
        }
      }
    }
  }
}
```

With `importChecks` set to `false`, `turbo boundaries` skips reading your source files, so no import violations are reported (including the type-only import check for type declaration packages). Tag rules and circular dependency detection still run. `importChecks` defaults to `true` and can only be set in the root `turbo.json`.

If you use a [baseline](#adopting-boundaries-in-an-existing-repository), its entries for import rules (`import-leaves-package`, `package-not-found`, and `not-type-only-import`) are left alone while import checks are disabled: they're not reported as stale, and `turbo boundaries --update-baseline` keeps them.

## Adopting boundaries in an existing repository

Large repositories often have existing violations that can't all be fixed before enabling `turbo boundaries` in CI. A baseline file records the violations that exist today so that only new violations fail the check. Fix the recorded violations over time to ratchet the baseline down.

To create or update the baseline, run:

```bash title="Terminal"
turbo boundaries --update-baseline
```

This checks your repository and writes every current violation to `boundaries-baseline.json` at the root of the repository. Commit this file. From then on, `turbo boundaries`:

- Suppresses violations recorded in the baseline, and reports how many were suppressed.
- Fails on violations that are not recorded in the baseline.
- Fails on stale baseline entries: violations that were recorded but have since been fixed. Run `turbo boundaries --update-baseline` to remove them, so that a fixed violation can't be reintroduced without anyone noticing.

The baseline is a machine-owned file. Rather than editing it by hand, rerun `turbo boundaries --update-baseline`.

### Baseline format

Entries are grouped by package and don't contain line numbers, so unrelated edits to a file don't invalidate the baseline:

```json title="./boundaries-baseline.json"
{
  "version": 1,
  "violations": {
    "//": [
      {
        "rule": "circular-dependency",
        "cycle": ["@repo/a", "@repo/b"],
        "count": 1
      }
    ],
    "web": [
      {
        "rule": "denied-tag",
        "package": "@repo/internal-ui",
        "tag": "internal",
        "count": 1
      },
      {
        "file": "apps/web/src/index.ts",
        "rule": "package-not-found",
        "import": "lodash",
        "count": 2
      }
    ]
  }
}
```

Each entry identifies a violation by its package, its file (relative to the repository root), its rule, and its subject (the import, the related package and tag, or the packages in the cycle). Within a package, entries without a file come first, followed by entries sorted by file. `count` is the number of times that violation occurs, so adding one more identical violation to the same file fails the check.

Circular dependencies are recorded under the root package, `//`, and identified by every package that is part of the cycle. If another package joins an existing cycle, the cycle is reported as a new violation.

| Rule                    | Violation                                                               |
| ----------------------- | ----------------------------------------------------------------------- |
| `import-leaves-package` | Importing a file outside of the package's directory                     |
| `package-not-found`     | Importing a package that is not a dependency                            |
| `not-type-only-import`  | Importing a type declaration package without a type-only import         |
| `tag-not-in-allowlist`  | Depending on, or being depended on by, a package without an allowed tag |
| `denied-tag`            | Depending on, or being depended on by, a package with a denied tag      |
| `denied-package`        | Depending on an npm package listed in `denyPackages`                    |
| `circular-dependency`   | A cycle in the package graph                                            |

Some problems can't be added to the baseline because they mean that code is not being checked at all: files that fail to parse, paths that aren't valid UTF-8, and invalid `boundaries` configuration. `turbo boundaries --update-baseline` still reports these and exits with an error until they're fixed.

### Filtering

When you use `--filter`, only the selected packages are checked. Baseline entries for other packages are left alone: they're not reported as stale, and `turbo boundaries --update-baseline --filter=<package>` only replaces the entries for the selected packages. Circular dependencies are always checked, as are entries for packages that no longer exist.

### `turbo query`

The baseline only applies to `turbo boundaries`. The `boundaries` field of [`turbo query`](/docs/reference/query) always reports every violation, including those recorded in the baseline, so tools built on it see the raw state of the repository.

### Configuring the baseline location

Use the [`boundaries.baseline`](/docs/reference/configuration#baseline) key in your root `turbo.json` to store the baseline somewhere else:

```json title="./turbo.json"
{
  "boundaries": {
    "baseline": "config/boundaries-baseline.json"
  }
}
```
