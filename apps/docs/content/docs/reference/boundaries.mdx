Boundaries ensure that Turborepo features work correctly by checking for package manager Workspace violations.

```bash title="Terminal"
turbo boundaries
```

<Callout type="info" title="Boundaries RFC">
  This feature is experimental, and we're looking for your feedback on [the
  Boundaries RFC](https://github.com/vercel/turborepo/discussions/9435).
</Callout>

This command will notify for two types of violations:

- Importing a file outside of the package's directory
- Importing a package that is not specified as a dependency in the package's `package.json`

## Tags

Boundaries also has a feature that lets you add tags to packages. These tags can be used to create rules
for Boundaries to check. For example, you can add an `internal` tag to your UI package:

```json title="./packages/ui/turbo.json"
{
  "tags": ["internal"]
}
```

And then declare a rule that packages with a `public` tag cannot depend on packages with an `internal` tag:

```json title="./turbo.json"
{
  "boundaries": {
    "tags": {
      "public": {
        "dependencies": {
          "deny": ["internal"]
        }
      }
    }
  }
}
```

Alternatively, you may want `public` packages to only depend on other `public` packages:

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "public": {
        "dependencies": {
          "allow": ["public"]
        }
      }
    }
  }
}
```

Likewise, you can add restrictions for a tag's dependents, i.e. packages that import packages with the tag.

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "private": {
        "dependents": {
          "deny": ["public"]
        }
      }
    }
  }
}
```

Package names can also be used in place of a tag in allow and deny lists.

```json title="turbo.json"
{
  "boundaries": {
    "tags": {
      "private": {
        "dependents": {
          "deny": ["@repo/my-pkg"]
        }
      }
    }
  }
}
```

Tags allow you to ensure that the wrong package isn't getting imported somewhere in your graph. These rules are
applied even for dependencies of dependencies, so if you import a package that in turn imports another package
with a denied tag, you will still get a rule violation.

## Adopting boundaries in an existing repository

Large repositories often have existing violations that can't all be fixed before enabling `turbo boundaries` in CI. A baseline file records the violations that exist today so that only new violations fail the check. Fix the recorded violations over time to ratchet the baseline down.

To create or update the baseline, run:

```bash title="Terminal"
turbo boundaries --update-baseline
```

This checks your repository and writes every current violation to `boundaries-baseline.json` at the root of the repository. Commit this file. From then on, `turbo boundaries`:

- Suppresses violations recorded in the baseline, and reports how many were suppressed.
- Fails on violations that are not recorded in the baseline.
- Fails on stale baseline entries: violations that were recorded but have since been fixed. Run `turbo boundaries --update-baseline` to remove them, so that a fixed violation can't be reintroduced without anyone noticing.

The baseline is a machine-owned file. Rather than editing it by hand, rerun `turbo boundaries --update-baseline`.

### Baseline format

Entries are grouped by package and don't contain line numbers, so unrelated edits to a file don't invalidate the baseline:

```json title="./boundaries-baseline.json"
{
  "version": 1,
  "violations": {
    "//": [
      {
        "rule": "circular-dependency",
        "cycle": ["@repo/a", "@repo/b"],
        "count": 1
      }
    ],
    "web": [
      {
        "rule": "denied-tag",
        "package": "@repo/internal-ui",
        "tag": "internal",
        "count": 1
      },
      {
        "file": "apps/web/src/index.ts",
        "rule": "package-not-found",
        "import": "lodash",
        "count": 2
      }
    ]
  }
}
```

Each entry identifies a violation by its package, its file (relative to the repository root), its rule, and its subject (the import, the related package and tag, or the packages in the cycle). Within a package, entries without a file come first, followed by entries sorted by file. `count` is the number of times that violation occurs, so adding one more identical violation to the same file fails the check.

Circular dependencies are recorded under the root package, `//`, and identified by every package that is part of the cycle. If another package joins an existing cycle, the cycle is reported as a new violation.

| Rule                    | Violation                                                               |
| ----------------------- | ----------------------------------------------------------------------- |
| `import-leaves-package` | Importing a file outside of the package's directory                     |
| `package-not-found`     | Importing a package that is not a dependency                            |
| `not-type-only-import`  | Importing a type declaration package without a type-only import         |
| `tag-not-in-allowlist`  | Depending on, or being depended on by, a package without an allowed tag |
| `denied-tag`            | Depending on, or being depended on by, a package with a denied tag      |
| `circular-dependency`   | A cycle in the package graph                                            |

Some problems can't be added to the baseline because they mean that code is not being checked at all: files that fail to parse, paths that aren't valid UTF-8, and invalid `boundaries` configuration. `turbo boundaries --update-baseline` still reports these and exits with an error until they're fixed.

If a file can't be checked (for example, because of a syntax error), its baseline entries are left alone: they're not reported as stale, and `turbo boundaries --update-baseline` keeps them unchanged until the file can be checked again.

### Filtering

When you use `--filter`, only the selected packages are checked. Baseline entries for other packages are left alone: they're not reported as stale, and `turbo boundaries --update-baseline --filter=<package>` only replaces the entries for the selected packages. Circular dependencies are always checked, as are entries for packages that no longer exist.

### `turbo query`

The baseline only applies to `turbo boundaries`. The `boundaries` field of [`turbo query`](/docs/reference/query) always reports every violation, including those recorded in the baseline, so tools built on it see the raw state of the repository.

### Configuring the baseline location

Use the [`boundaries.baseline`](/docs/reference/configuration#baseline) key in your root `turbo.json` to store the baseline somewhere else:

```json title="./turbo.json"
{
  "boundaries": {
    "baseline": "config/boundaries-baseline.json"
  }
}
```
